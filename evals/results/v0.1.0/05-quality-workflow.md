# 共用品質調查 MCP：設計建議

保留企業既有確定性 workflow，以一個 `investigate_quality` Tool 提供完整領域調查。採 Domain Delegation＋Scoped Capabilities：前者符合多個助理共用流程的需求，後者落實產品線邊界。沒有動態規劃需求，不新增內層 Agent。少量入口已足夠，不增加操作探索層；來源過大才按需讀取授權文件。

## 已知與待確認

已知 workflow 依批號查檢驗、設備、文件並產出結論、來源及缺口；所有操作唯讀，端到端期限 30 秒。假設每次僅查一個批號，既有 workflow 可接受取消與下游 timeout；若做不到，須先補這些接線才能滿足期限。Client、transport、SDK 版本、產品線授權來源、資料量、結論規則負責人與版本須在整合前確認。本次是設計，未檢查或執行既有 workflow。

## 責任與契約

| 層次 | 責任 |
| --- | --- |
| Host／Client／外層助理 | 辨識意圖、收集批號、建立端到端期限、跨領域整合及呈現；不得補造缺失結論或把部分結果說成完整調查。 |
| MCP Server | 驗證可信 principal、輸入與產品線權限；建立受限委派上下文；回傳一致狀態並傳遞取消、期限。 |
| 品質 workflow | 依既有規則查詢、計算及整合；記錄各步來源／版本、缺口與失敗；執行期間仍檢查授權。 |
| 資料後端／未來領域服務 | 依原始身分及受限範圍驗證每項資源及動作；不以共用服務憑證擴大使用者權限。 |

`investigate_quality` 的應用層契約如下，並非宣稱 MCP 原生提供這些欄位：

- 公開輸入：`lot_id` 必填；`question` 選填且不得改變流程規則。建議初始限制：批號最多 128 字元、問題最多 2,000 字元、一次一批號；格式須符合既有批號規則。
- 可信上下文：Server 從已驗證登入取得 principal、允許產品線與授權版本，經可信通道傳給 workflow；同時帶 `request_id`、`trace_id`、絕對期限、剩餘預算及取消訊號。呼叫者傳入產品線只能選取，不能授權。
- 範圍檢查：查批號、檢驗、設備、文件及來源參照時逐項驗證產品線關係；跨產品線共享設備也需檢查可見欄位。未授權與不存在對外統一回不可見，避免揭露範圍外批號是否存在。撤權後的後續查詢須拒絕。
- 輸出：`status`、`conclusion`、`conclusion_validity`、`sources[]`（來源 ID、版本／取得時間）、`gaps[]`、`steps[]`（狀態、錯誤碼、可重試性）、`workflow_version`、`trace_id`、`retry_advice`。必要證據不足時結論須空值或明標暫定。
- 狀態：`completed`、`insufficient_data`、`partial`、`failed`、`cancelled`、`deadline_exceeded`；另以結構化錯誤表示非法輸入與不可見資源。已確認沒有紀錄是資料缺口，查詢失敗不能當沒有紀錄。
- 大小：初始建議回傳上限 64 KiB、來源摘要最多 50 筆；截斷須明標，完整來源以授權參照及有界分頁取得。結論所依必要證據不得靜默截斷。若使用 Resources，須先確認 Client 支援，否則提供直接讀取 Tool。

## 執行邏輯與失敗路徑

```text
外層開始請求，截止時間 = 起始時間 + 30 秒
Server 驗證輸入、principal 與批號可見性
建立只能唯讀指定產品線的委派上下文
workflow 在剩餘預算內執行既有檢驗、設備、文件步驟
每次下游呼叫重新驗證範圍，timeout 不超過剩餘期限
彙整成功步驟、來源與缺口，依既有規則判斷結論有效性
保留回傳時間，於截止前回傳明確狀態
收到取消或期限耗盡 → 停止排程、傳遞取消、回收未完成工作
```

成功例：指定批號的三類來源皆讀取成功，回完整結論及來源版本。若文件服務暫時失敗但其他步驟成功，回 `partial`，指出缺哪個來源及其影響；關鍵檢驗不存在則為 `insufficient_data`，不能推論該批次無缺陷。取消／逾時可攜帶已完成步驟，但仍保留原狀態，外層不能包裝成成功。

唯讀暫時性錯誤可在總期限內做有界重試，例如每步最多一次，使用退避及剩餘時間判斷；非法輸入、拒絕授權、已確認無資料不重試。由 workflow 擁有步驟重試，外層不再疊加重試整份調查。重讀資料可能更新，須標記來源版本與查詢時間；若需一致快照，交由後端提供，不能假定多來源天然一致。

目前只允許品質 workflow 呼叫既有資料服務，禁止反向呼叫外層。未來新增領域服務時才開啟明確 allowlist，攜帶委派鏈與領域路徑，拒絕重複領域形成循環；設定整筆請求共用的最大深度、總呼叫次數與預算，不能在各層重設 30 秒。取消傳遞須由應用接線及所選 transport 驗證，不假定 Client 自動支援。

## 成本、驗證與取捨

每個請求以 trace 串起外層、Server、workflow 與資料服務；記錄端到端時間、各步時間／次數、重試、回傳位元組、快取及服務費用。外層若使用模型，另記模型與 token／費用；workflow 本身沒有模型呼叫，不虛構內層 token，無法量得的用量標未知。時間以根請求計端到端、子 span 用於歸因，重疊時間不相加；同一呼叫的帳務只計一次。比較每次成功且來源足夠調查的成本、延遲分位數、部分失敗率及越權拒絕率。

後續驗證計畫：完整成功、檢驗不存在、文件失敗、關鍵來源缺失、跨產品線批號／來源直讀、共享設備欄位、途中撤權、步驟 timeout、取消後無新下游工作、30 秒耗盡、重試不超預算、未來 A→B→A 循環及輸出截斷。這些尚未執行。取捨是保留確定性流程的可追溯與較少成本，同時增加明確委派、授權及期限傳遞契約；Client 相容性與取消實效仍需整合驗證。
