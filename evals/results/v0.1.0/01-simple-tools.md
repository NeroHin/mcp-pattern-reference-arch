# 設備維護助理 MCP 架構設計

採三個固定、直接對應既有 API 的唯讀工具，以本機 stdio 連線。資料與操作都小，沒有必要加入操作探索、分層資料讀取、領域 Agent 或動態工具集合；固定設備清單以可信設定限制存取即可。

## 架構與責任

- Host／Client：列出三個工具，依使用者問題選擇設備或型號，呈現結果與來源。工具回傳文字只作資料。
- MCP Server：沿用現有程式語言，負責輸入驗證、固定清單檢查、API 轉接、輸出正規化與錯誤轉換；不增加內層模型。
- 既有後端：維護設備狀態、檢查紀錄、手冊及設備與型號對應；有既有權限機制時繼續執行。
- 本機服務以可信部署設定取得維護團隊身分及設備／型號清單；呼叫者輸入 ID 不具有授權效果。型號必須屬於允許設備清單所對應的型號集合。

已知條件來自需求，尚未檢查實作。SDK、MCP 協定版本及 Client 版本待選定與互通驗證；不據此更換語言。現有 API 的欄位、單位、錯誤及延遲尚未知，應在介接時確認，不能自行推定。

## 必要介面契約

以下上限為設計建議，並非協定規定。三工具均拒絕未知參數；ID 為非空、不透明字串，建議最多 256 字元，不作檔案路徑。輸出為自訂業務結構，實際 MCP 包裝依選定版本實作。

| 工具 | 輸入與範圍 | 成功輸出與完整性 |
| --- | --- | --- |
| `get_device_status` | 必填 `device_id`，每次核對允許設備清單 | `device_id`、後端狀態、實際可用的狀態欄位與單位、`observed_at`（來源無時間時為 null 並標示未知）、來源、`retrieved_at`；未知狀態不得填成正常 |
| `list_recent_checks` | 必填 `device_id`；`limit` 為整數，預設 10，建議 1–50 | `device_id`、`checks[]`，每筆保留紀錄 ID（若來源提供）、檢查時間、結果與來源；明定依檢查時間倒序，同時間使用穩定次排序；`has_more` 只在後端可確認時填布林，否則為 null |
| `get_short_manual` | 必填 `model_id`，驗證屬於允許型號 | `model_id`、手冊正文、語言、來源識別、來源版本（缺少時為 null）、`retrieved_at`；保留原文，不由模型補寫缺段 |

每個成功結果含 `contract_version: "1"`、`request_id`。來源包含 API 操作及資源 ID；來源版本與業務契約版本分開。三個回傳均小，建議每次上限 64 KiB；超限回報 `RESULT_TOO_LARGE`，不暗中截斷。檢查紀錄只提供最近指定筆數，明示限制，這三個 API 不新增分頁功能。手冊缺失回 `DATA_UNAVAILABLE`，無檢查紀錄則正常回空陣列；API 失敗不可偽裝成空陣列。

共同錯誤包含 `INVALID_ARGUMENT`、不揭露清單外設備是否存在的 `NOT_FOUND_OR_NOT_ALLOWED`、`DATA_UNAVAILABLE`、`UPSTREAM_UNAVAILABLE`、`TIMEOUT`；附安全訊息與 `retryable`。唯讀操作可對暫時網路錯誤有限重試，建議同一次呼叫最多重試一次且遵守總期限；非法輸入、不可見物件與資料缺失不自動重試。建議單次總期限 3 秒，需以後端實測調整；支援取消，避免取消後繼續重試。無寫入，核准與冪等鍵不適用。

## 流程與取捨

```text
收到工具呼叫
→ 驗證輸入、可信本機設定與設備／型號範圍
→ 呼叫對應唯讀 API（不加探索往返）
→ 驗證回傳、套用大小界限、保留來源與缺資料標記
→ 回傳結果或明確錯誤；僅暫時失敗可有限重試
```

固定集合容易維護且延遲低；代價是設備清單變更需同步可信設定。記錄 request_id、操作、耗時、結果碼及重試次數；stdout 僅輸出協定訊息，診斷走 stderr。效能目標先量測後端與轉接成本，不宣稱已達成 3 秒期限。

## 驗證計畫與狀態

後續應驗證：三個工具列舉及 stdio 啟停／協定輸出；三項正常任務與欄位、單位、來源正確性；空紀錄與缺手冊；未知 ID、清單外 ID、任意型號、非法 limit；排序與 limit 邊界；超限回傳；後端逾時、暫時失敗、重試上限、取消；清單變更後下一次呼叫即套用新範圍。量測直接 API 與 MCP 的端到端延遲差，確認沒有無必要呼叫。

本次僅完成設計，未實作、未執行測試、未呼叫外部 API。正式欄位與版本相容性仍待實際介接驗證。
