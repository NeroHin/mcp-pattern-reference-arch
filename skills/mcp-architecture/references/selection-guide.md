# 選型流程

## 先確認責任

建立需求表：代表性任務與成功條件、既有資料／操作、業務規則的維護者與版本、計算位置、身分／資源範圍、讀寫風險、資料及操作目錄規模、延遲／成本預算、Client 能力與 transport。未知值標為假設或待確認。

最小基線是少量清楚且能完成任務的直接工具。穩定上下文可考慮 Resources，使用者主動啟動的流程可考慮 Prompts；依 Client 實際支援決定。

## 可組合的五個設計軸

| 訊號 | 候選 | 主要代價／先決條件 |
| --- | --- | --- |
| 已知任務、專案或角色，許多能力不相關 | Scoped Capabilities | 能力設定與授權可能漂移；每次操作仍需檢查權限 |
| 大內容中只需一小部分 | Progressive Disclosure | 額外往返、摘要遺漏、版本變動；全量計算可能仍要全讀 |
| 大型或常變動的操作目錄 | Discover + Execute | 搜尋品質、規格版本與派送驗證；少量入口仍可能權限很大 |
| 統一定義、單位、時間與彙總規則 | Semantic Contract | 先具備領域定義與維護者；模型仍可能選錯參數 |
| 多個應用共用完整領域流程 | Domain Delegation | 契約、失敗責任與端到端成本；內層 Agent 要有採用理由 |

## 決策偽程式碼

```text
讀取需求與實作證據，標示影響選型的未知條件
建立可完成代表性任務的直接介面基線
確定業務定義、計算、授權與協調的負責方
候選 = 基線
按任務／角色／範圍限縮能力有價值 → 評估 Scoped
分段讀取可避免無關內容 → 評估 Progressive
操作規格按需取得有價值 → 評估 Discover + Execute
正式業務定義需統一管理 → 評估 Semantic
領域流程值得共用 → 評估 Domain
各條件獨立判斷，允許組合
檢查前提、額外成本、Client 支援及所有入口的授權邊界
走過成功、空結果、失敗與重試路徑
交付選擇、契約、證據及驗證計畫
```

## 組合與退回基線

- Scoped 可與其他四種組合；同時限制可找到的資料／操作與真正可執行的動作。
- Progressive 找資料，Discover 找操作；可各自存在或一起採用。
- Semantic 管理業務定義；Domain 協調領域任務；組合時保留來源、版本與責任。
- 正式口徑強制經由領域服務時，其他入口也須維持相同規則，避免未授權繞過。
- 幾支明確工具已足夠時保留基線。全量計算優先評估後端彙總；分段讀取可能有傳輸價值，但不預設省 token。
- 缺少可信業務定義時先確認定義，暫時查詢明確標示可信範圍。
- 需要生成程式組合且具備受控環境時才延伸 Code Mode；固定參數派送可獨立成立。

先檢查任務成功、來源完整、越權與錯誤處理，再比較往返、回傳大小、延遲與成本。單次用量排名不能決定架構。
